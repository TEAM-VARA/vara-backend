# 중간발표 예상 질문 — Risk Scoring

> 코드(dev 브랜치) 기준으로 검증한 답변입니다. 형식은 팀원 인프라 Q&A(A1~A12)와 동일하게 한 줄 / 풀어서 / 반박 대비 / 주의로 구성했습니다.
> **정정 주의:** 일부 설계 문서엔 "Local = 0.6×노출 + 0.4×AttackPath"로 적혀 있으나, **실제 코드는 Local = 노출(0~20) + AttackPath(0~80)** 입니다. 발표는 코드 기준으로 통일하세요.

## B1. 위험도를 어떻게 점수화하나? 공식은?

**한 줄:** CVE 자체 위험(Global)과 배포 환경 위험(Local)을 가중 결합한 뒤, 위험 조합 배수(Toxic)를 곱해 0~100으로 산정합니다.

**풀어서:**

```
Final = (Global × 0.6 + Local × 0.4) × Toxic_Multiplier   (상한 100)

Global (0~100) = (CVSS/10 × 0.4 + EPSS × 0.3 + SSVC × 0.3) × 100
  - CVSS: 취약점의 본질적 심각도 (표준)
  - EPSS: 실제 악용될 확률 (예측, FIRST 제공)
  - SSVC: 악용 관측 여부 (KEV 등재=1.0 / ExploitDB PoC=0.5 / 없음=0.0)

Local (0~100) = 노출 기여(0~20) + 공격경로 기여(0~80)
  - 노출(Exposure): 인터넷에 노출됐는가 = "공격 가능성"
  - 공격경로(Attack Path): RBAC + Network + Mount 3축 = "뚫렸을 때 영향 범위"

Toxic_Multiplier: 위험 조합 시 배수 (Critical ×1.5 / High ×1.3 / Medium ×1.2)
```

- 등급(4단계): **emergency ≥ 80 / warning ≥ 50 / caution ≥ 20 / safe < 20**
- 핵심 사상: "심각한 CVE"가 아니라 **"우리 환경에서 실제로 위험한 CVE"**를 위로 올립니다. 같은 CVE라도 인터넷에 노출되고 권한이 과한 파드면 점수가 올라갑니다.

**반박 대비:**
- *"그냥 CVSS만 쓰면 안 되나?"* → CVSS는 CVE 자체 점수라 환경을 모릅니다. 내부 전용 파드의 CVSS 9.8과 인터넷 노출 파드의 9.8을 똑같이 취급하면 우선순위가 안 나옵니다. 그래서 Local(환경)을 곱이 아니라 가중합으로 더하고, 조합 위험만 곱(Toxic)으로 증폭합니다.
- *"가중치 0.6/0.4는 왜?"* → B8 참조.

**주의(솔직한 한계):** 가중치는 현재 코드에 하드코딩이며, 사용자 조정 기능은 다음 과제입니다. Toxic 룰 10개 중 2개(TOXIC-003/005)는 현재 비활성입니다.

## B2. 왜 트래픽 양이 아니라 "도달 가능성"인가?

**한 줄:** 공격은 경로를 "한 번" 타면 되지, 트래픽이 많아서 위험한 게 아니기 때문입니다. 위험은 양이 아니라 "닿을 수 있느냐"로 결정됩니다.

**풀어서:**
- 트래픽 양이 많다 = 정상 업무가 바쁘다는 뜻이지 위험이 아닙니다. 오히려 공격자는 **딱 한 번의 연결**로 측면 이동(lateral movement)을 합니다. 평소 트래픽이 0이어도 "닿을 수 있는 경로"가 있으면 위험합니다.
- 그래서 Blast Radius는 "A가 B에 **도달 가능한가**"(reachability)로 그립니다. 도달 가능한 파드가 곧 잠재적 폭발 반경입니다.
- 다만 **단순 도달성은 의미가 없습니다.** Kubernetes 기본망은 flat network라 NetworkPolicy가 없으면 모든 파드가 서로 도달 가능 → "전체가 폭발 반경"이라는 무의미한 결론. 그래서 우리는 **eBPF로 실측한 통신(observed)** 위에서 도달성을 계산해 노이즈를 걷어냅니다.
- 트래픽 "양"은 위험 점수가 아니라 **엣지 표시(굵기)용 보조 신호**로만 씁니다 (실제 통신했다는 증거 수준).

**반박 대비:**
- *"그럼 트래픽 양은 왜 수집하나?"* → 굵기/시각화 + "선언만 됐고 실제 안 쓰는 경로"를 걸러내는 필터로 씁니다. 점수의 분자가 아닙니다.
- *"한 번도 통신 안 한 경로는 놓치는 것 아닌가?"* → 그래서 계층(Tier)으로 봅니다. Tier1 eBPF 실측(가장 확실), Tier3 NetworkPolicy 선언상 허용(잠재). 실측을 메인으로 깔고 선언 경로를 컨텍스트로 보여줍니다.

**주의:** 현재 데모 클러스터는 eBPF 실측 트래픽이 적어 observed 그래프가 빈약할 수 있습니다. 시연 시 시드 데이터 전략을 PM과 합의해야 합니다.

## B3. CVE가 수천 개 나올 텐데 어떻게 우선순위를 매기나?

**한 줄:** 4단계 등급으로 자르고, "환경 맥락 + 악용 가능성 + 위험 조합"으로 상위를 끌어올려 **고쳐야 할 소수**만 위에 오게 합니다.

**풀어서:**
- 단순 CVE 나열은 수천 개라 의미가 없습니다. 우리는 세 층으로 줄입니다:
  1. **악용 가능성으로 거르기** — EPSS(악용 확률) + SSVC(KEV 등재/PoC 존재)로, 실제로 악용되는 소수를 위로. 대부분의 CVE는 EPSS가 매우 낮습니다.
  2. **환경 맥락으로 거르기** — 인터넷 노출 + 과한 권한 + 위험한 마운트가 결합된 파드의 CVE를 우선. 내부 전용·저권한 파드의 같은 CVE는 아래로.
  3. **위험 조합(Toxic)으로 증폭** — "인터넷 노출 + 알려진 익스플로잇" 같은 조합은 배수로 올려 최상단에.
- 결과적으로 emergency 등급(≥80)에 오는 건 수천 중 소수이고, 그게 "지금 당장 고쳐야 할 목록"입니다.
- 추가로 **eBPF 실측 필터**: 고위험 이미지라도 런타임에 실제 쓰이는 건 일부입니다(업계 통계상 부여 권한의 ~90%가 미사용). 실측으로 "실제로 돌아가는" 것에 가중해 우선순위를 더 정밀하게 합니다.

**반박 대비:**
- *"그래도 emergency가 수백 개면?"* → Toxic 배수와 Blast Radius(영향 범위)로 2차 정렬합니다. "이 파드 하나 뚫리면 N개로 번진다"가 큰 것부터.
- *"낮은 점수 CVE는 무시하나?"* → 무시가 아니라 등급으로 분류해 두는 겁니다. caution/safe는 모니터링 대상으로 남되 대응 우선순위에서 내려갑니다.

**주의:** "어느 파드부터 고쳐라" 순위를 신규 CVE 알림에 직접 싣는 건 다음 과제입니다(현재는 등급/점수 조회로 제공).

## B4. Global과 Local을 왜 분리했나?

**한 줄:** "CVE 자체가 얼마나 위험한가"와 "우리 환경에서 얼마나 위험한가"는 다른 질문이라, 섞으면 false positive가 생기기 때문입니다.

**풀어서:**
- Global은 본질적 위험(CVE 고유), Local은 맥락적 위험(배포 환경). 분리 안 하면 "CVSS는 낮은데 노출만으로 Critical" 같은 환경 기반 오탐, 반대로 "환경은 안전한데 CVSS만으로 긴급" 같은 오탐이 섞입니다.
- 분리하면 발표에서 **"왜 이 점수인지"를 두 축으로 설명**할 수 있습니다 (설명가능성). Breakdown API가 두 기여도를 따로 보여줍니다.

**근거 출처:** V-Score 논문(2024) — Global+Local 2계층 구조가 CVSS 단독 대비 약 2배 정확도(75% vs 39%). NIST 800-37 RMF의 Risk = Impact × Likelihood 사상도 같은 맥락.

## B5. Toxic Combination이 뭔가? 왜 곱셈인가?

**한 줄:** 단독으론 낮지만 조합되면 위험이 급증하는 패턴("1+1=3")을 곱셈 배수로 반영합니다.

**풀어서:**
- 예: "인터넷 노출"(단독 보통) + "알려진 익스플로잇"(단독 보통) → 조합되면 실제 침해 가능성 급증. "privileged 컨테이너 + secret 마운트", "측면 이동 준비 상태(LATERAL_MOVEMENT_READY)" 등 10개 룰.
- **왜 곱셈?** 더하기는 조합의 비선형 위험을 못 살립니다. 곱셈(배수)은 "두 조건이 동시에 참일 때만" 증폭하는 구조라 조합 위험을 정확히 표현합니다. Qualys TruRisk도 인터넷 노출을 곱셈 인자로 씁니다.
- 배수: Critical ×1.5 / High ×1.3 / Medium ×1.2.

**반박 대비:** *"곱하면 점수가 100을 넘지 않나?"* → B6 참조 (의도된 신호이며 상한 처리함).

**주의:** 10개 룰 중 TOXIC-003 / TOXIC-005는 현재 비활성 상태입니다.

## B6. 점수가 100을 넘는 경우(raw 114.18)가 있던데?

**한 줄:** Toxic 배수로 원점수가 상한을 넘을 수 있는데, 이건 "위험 조합이 그만큼 심하다"는 신호이고, 최종 점수는 100으로 clamp합니다.

**풀어서:**
- 예: 가중합 76점 × Toxic 1.5 = raw 114.18. 최종 표시는 100(emergency)이지만, **Breakdown의 formula 문자열엔 raw 값을 투명하게 남깁니다** ("...= 114.18 → 상한 적용 100.00").
- 발표 포인트: "상한을 14점이나 초과하는 위험 조합"이라는 표현으로 심각도를 직관적으로 전달할 수 있습니다("1+1=3").
- 6/7에 `clamp(final, 0, 100)` 패치 적용 — 등급 경계와 FE 표시를 위해 최종은 0~100으로 고정.

## B7. CVSS·EPSS·KEV·ExploitDB·SSVC를 다 쓰면 중복 아닌가?

**한 줄:** 역할을 분리해 이중 계산을 막았습니다. 특히 ExploitDB는 별도 항목이 아니라 SSVC 축으로 흡수했습니다.

**풀어서:**
- 5개 신호의 역할: **CVSS=표준 심각도, EPSS=악용 예측 확률, SSVC=악용 관측(KEV/PoC)**. 표준성·예측·실측의 균형.
- **이중 계산 함정:** EPSS는 내부 피처로 이미 ExploitDB 정보를 학습에 씁니다. ExploitDB를 또 별도 점수 항목으로 더하면 같은 신호를 두 번 세는 셈. 그래서 ExploitDB는 **SSVC의 Exploitation 축**(PoC=0.5)으로만 반영해 중복을 제거했습니다.
- SSVC 3단계: KEV 등재 → Active(1.0), ExploitDB PoC 존재 → PoC(0.5), 둘 다 없음 → None(0.0). CISA SSVC 표준을 따릅니다.

**근거 출처:** CISA SSVC(Exploitation 축), CISA Vulnrichment(무료 SSVC 데이터 ~64K CVE).

## B8. 가중치(0.6/0.4, 4:3:3 등)는 자의적 아닌가?

**한 줄:** 공신력 있는 선행 모델에서 차용했고, 자의적 상수가 아니라 "조정 가능한 정책 파라미터"로 설계했습니다.

**풀어서:**
- Global의 CVSS:EPSS:SSVC = 4:3:3 → 표준(CVSS)에 무게를 두되 예측·실측을 균형 있게. EPSS·SSVC 합(0.6)이 CVSS(0.4)보다 커서 "실제 악용 신호"를 더 본다는 의도.
- Global:Local = 0.6:0.4 → CVE 자체 위험을 기본으로, 환경 맥락이 보정. V-Score의 2계층 구조 참고.
- 솔직하게: **절대적으로 검증된 황금비는 없습니다.** 그래서 가중치를 **사용자가 조정 가능하게 하는 것**을 로드맵에 두고 있습니다(현재 하드코딩). 조직마다 "노출을 더 본다/권한을 더 본다"가 다를 수 있으니까요.

**근거 출처:** V-Score, Tenable VPR(Threat × Impact 곱 구조), Qualys TruRisk(노출 곱셈 인자).

## B9. eBPF 실측이 점수에 어떻게 반영되나? (정적 분석과 차이)

**한 줄:** 정적 점수(선언 기반)에 런타임 실측을 더해 보정합니다 — "줬지만 안 쓰는 권한", "실제로 일어난 통신"을 반영해 오탐을 줄입니다.

**풀어서:**
- Phase 1(정적): K8s 매니페스트·RBAC·SBOM 등 "선언된" 정보로 점수 산정.
- Phase 2(런타임 보강): eBPF로 관측한 실제 행위를 반영. 예: `overgrant_ratio`(부여됐지만 미사용인 권한 비율 — 업계 통계상 ~90% 미사용), 실제 외부 통신 여부, host network 사용 여부 등.
- 효과: "권한은 과하게 줬지만 런타임엔 안 쓰는" 파드는 위험을 낮추고, "실제로 외부와 통신하는" 파드는 노출 위험을 높입니다. 선언만 보는 도구 대비 정밀합니다.

**주의:** 런타임 보정 배수는 과증폭 방지를 위해 1.5로 clamp합니다.

## B10. 인터넷 노출을 어떻게 판단하나? K8s 정보만으로 되나?

**한 줄:** K8s 메타데이터만으로는 부족하고, AWS API(Security Group·ELB scheme 등)까지 봐야 실제 도달성을 알 수 있습니다.

**풀어서:**
- K8s 레벨: Service 타입(ClusterIP/NodePort/LoadBalancer), Ingress, NetworkPolicy로 1차 추정.
- 하지만 진짜 "인터넷에서 닿는가"는 **ALB scheme(internet-facing vs internal), Security Group inbound 규칙, VPC 퍼블릭 서브넷 라우팅**을 봐야 확정됩니다 → aws-reader가 수집한 AWS 데이터 활용.
- 현재 노출 점수는 노출 여부에 따라 Local에 최대 20점 기여. ("공격 가능성 여부" 신호)

**주의(솔직한 한계):** ALB scheme·IGW·서브넷 라우팅을 결합한 "실도달성 정밀 판정"은 데이터(SG/KMS/CloudTrail)는 확보했으나 점수 연계 로직은 보강 중입니다. 현재는 선언 기반 위주.

## B11. "자산 중요도 자동 추론"이 차별점이라는데, Tenable ACR과 뭐가 다른가?

**한 줄:** 기업이 안 알려줘도 클러스터가 스스로 알려주는 정보(실측 트래픽·권한·노출)를 그래프 중심성(PageRank)으로 합성해 **Pod 단위**로 중요도를 산출합니다.

**풀어서 (Tenable ACR과 비교):**
1. **단위**: ACR은 주로 호스트 단위, 우리는 **Pod 단위**(컨테이너 환경에 맞음).
2. **근거**: ACR은 정적 속성 위주, 우리는 **eBPF 실측 통신 그래프** 기반.
3. **수작업**: 수동 태깅 없이 클러스터가 내보내는 정보로 자동 산출.
- 구현: 실측 트래픽 토폴로지 + RBAC 권한 + 노출 정보를 그래프로 만들고 PageRank로 "이 클러스터에서 중심적인 파드"를 찾습니다. 중심성 높은 파드 = 뚫리면 영향 큰 자산.

**반박 대비:** *"ACR 같은 게 이미 있지 않나?"* → 존재를 인정하되, Pod 단위·실측 그래프·무태깅이라는 점에서 컨테이너 환경에 특화된 차별화라고 답합니다. ("없다"고 단정하지 말 것.)

**주의:** PageRank 중심성 계산은 구현·자동 실행되고 있으나, 그 값을 Risk Score(blast criticality)에 직접 연결하는 건 진행 중입니다(현재 일부 고정값).

---

## B12. 점수가 맞다는 걸 어떻게 검증/신뢰하나? (설명가능성)

**한 줄:** 모든 점수는 **투명한 공식 + 한국어 요인 설명 + raw 값 노출**로 분해해 보여줍니다(Breakdown API). 블랙박스가 아닙니다.

**풀어서:**
- Breakdown API: 한 파드의 Final이 어떻게 나왔는지 — Global/Local 기여도, 각 신호(CVSS/EPSS/SSVC) 값, Toxic 배수, formula 문자열("(76.0×0.6 + 50.0×0.4)×1.5 = 114.18 → 100")까지 분해.
- 각 요인에 한국어 해석을 붙여 "왜 이 점수인지"를 비전문가도 이해 가능.
- 경쟁사 대비(Orca 0~99 알고리즘 비공개, Wiz는 toxic을 점수 아닌 이슈 분류로만): 우리는 **공식과 raw를 공개**하는 설명가능성이 강점.

## B13. 경쟁사(Wiz/Orca/Sysdig/Prisma) 대비 차별점은?

**한 줄:** ① 투명한 공식+formula 노출 ② 한국어 요인 해석(설명가능성) ③ Toxic을 정량 배수로 ④ 표준 입력 5종 완전 채택 ⑤ eBPF 실측 그래프 기반 Blast Radius + 한국형 ISMS-P 매핑.

**풀어서:**
- Wiz: toxic combination을 "이슈 분류"로만 쓰고 정량 점수는 없음 → 우리는 배수로 정량화.
- Orca: 0~99 점수지만 알고리즘 비공개 → 우리는 공식 공개.
- Sysdig: in-use 런타임 필터(실사용 ~15%)가 강점 → 우리도 eBPF 실측 필터 채택.
- Prisma: Risk Factor + EPSS 도입 → 우리는 5종 표준 신호 + SSVC까지.
- 한국 특화: **ISMS-P 매핑**은 글로벌 CNAPP이 비워둔 영역. ("ISMS-P 지원 CNAPP이 없다"고 단정 말고 "조사 범위에서 확인되지 않았다"로 표현.)
